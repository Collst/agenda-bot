# ADR-001: Architecture of the Committee Agenda Bot

**Status:** Accepted  
**Date:** April 2026  
**Author:** Committee Agenda Bot project  

---

## What is an ADR?

An Architecture Decision Record documents a significant architectural choice:
what was decided, why, what alternatives were considered, and what consequences
follow. ADRs live in the repository so that future maintainers — including
people who weren't present for the original decisions — can understand not just
*what* the system does but *why* it was built this way.

This document covers the major decisions made in building the system. Each
section follows the same structure: context (why a decision was needed),
decision (what was chosen), alternatives considered, and consequences
(what follows from the choice, including tradeoffs).

## ADR-001-A: Use LangGraph for pipeline orchestration

### Context

The agenda generation workflow is not a linear sequence. After drafting an
agenda, the system needs to review it for format and completeness, and
conditionally revise it if problems are found — potentially multiple times.
This loop, combined with multiple LLM calls that share state, requires
explicit orchestration.

### Decision

Use **LangGraph** for pipeline orchestration. LangGraph models the workflow
as a directed graph with typed state (`AgendaState`) flowing between nodes.
Conditional edges handle the review→revise loop. LangChain components
(chat models, prompt templates, structured output) are used inside nodes.

### Alternatives considered

**Plain Python with a loop** — feasible for the current workflow but becomes
difficult to maintain as branches and conditions accumulate. The control flow
is implicit (buried in `if` statements and `while` loops) rather than explicit
and inspectable. Adding a new conditional step requires understanding the
entire function.

**n8n for the full pipeline** — n8n is appropriate for routing between
services but not for logic that lives *inside* AI interactions. Once nodes
need to evaluate each other's output and loop conditionally, n8n's
abstractions work against you rather than for you.

**LangChain without LangGraph** — LangChain alone handles linear chains well
but has no native concept of conditional routing or shared mutable state
across steps. LangGraph adds exactly those capabilities on top of LangChain.

### Consequences

- The graph topology (nodes, edges, routing functions) is the authoritative
  description of the pipeline's control flow. New steps are added as nodes;
  new conditions are added as conditional edges.
- Each node is independently testable: unit tests can invoke a node function
  directly with a mock state dictionary.
- LangSmith traces map directly to the graph structure, making it easy to
  locate which node produced a problematic output.
- LangGraph is a relatively young library. Breaking changes between minor
  versions are possible and have occurred. Pin versions in `requirements.txt`.

## ADR-001-B: Switchable LLM backend via environment variable

### Context

Two competing requirements: (1) data governance — some stakeholders require
that committee data not leave the organization's control; (2) output quality
— cloud models currently produce better results for complex reasoning and
formatting tasks than locally-runnable models at equivalent cost.

Additionally, the system should be shareable with other organizations, some
of which may have enterprise cloud model access and no local inference
infrastructure.

### Decision

Abstract the LLM behind a factory function (`services/llm.py` → `get_llm()`)
that returns the appropriate LangChain chat model based on a single
environment variable (`LLM_BACKEND=anthropic` or `LLM_BACKEND=ollama`).
No other code changes are required to switch backends.

### Alternatives considered

**Hardcode one backend** — simpler initially, but makes the system
unsuitable for organizations with different requirements and prevents
quality comparisons during development.

**Two separate codebases** — obviously worse. Duplication is the enemy of
maintainability.

**Runtime selection per node** — allowing different nodes to use different
backends (e.g. Anthropic for inference, Ollama for formatting). Technically
possible and potentially useful (a heavier model for task inference, a
lighter one for review), but adds complexity before the simpler version
has been validated. Deferred to a future iteration.

### Consequences

- Switching backends requires only a `.env` change and a Docker restart.
- LangSmith traces are backend-agnostic — the same observability works
  regardless of which model is running.
- On Apple Silicon, Ollama must run natively (via Homebrew) rather than
  inside Docker to access the Apple Neural Engine. This means
  `OLLAMA_BASE_URL=http://host.docker.internal:11434` in `.env` for Docker
  contexts, and `http://localhost:11434` for scripts run directly on the Mac.
- Output quality difference between backends is observable and should be
  measured via LangSmith before concluding that a larger model is needed.
  Prompt quality improvements frequently close the gap.

### Amendment — May 2026: Gemini added as third backend

**Why added:** Local models (Ollama/Qwen2.5:14b) produced insufficient
instruction-following quality for the task inference and drafting nodes
despite prompt refinement. Anthropic's API produces strong results but
sends data to a third party. Gemini was added as a third option motivated
by two factors: (1) the committee's data already resides in Google
infrastructure, making Google's API a defensible data residency choice;
(2) Gemini 2.5 Flash produces materially better instruction-following than
the tested local models.

**Cost note:** Gemini's free tier is insufficient for this pipeline — a
single run exhausts the per-minute token quota. Billing must be enabled.
At paid tier rates, cost per run is about $0.13.

**Model string:** `gemini-2.5-flash` is the recommended starting point and was used during development.
`gemini-2.5-pro` is available if output quality requires further improvement
at marginally higher cost.

## ADR-001-C: Separate personas from task prompts

### Context

Early versions of the prompt files (e.g. `draft_agenda.txt`) combined two
distinct concerns in a single file: *identity* ("you are an expert committee
secretary") and *task instructions* (formatting rules, content rules, section
structure). As the system grew toward multiple agents with different roles,
this conflation became a maintenance problem — the identity claim in a task
prompt would conflict with a separately defined persona.

### Decision

Split prompts into two layers stored in separate directories:

- `agent/personas/*.md` — defines *who is reasoning*: role, domain,
  responsibilities, explicit boundaries. One file per organizational role.
- `agent/prompts/*.txt` — defines *what to do*: task instructions, formatting
  rules, output constraints. One file per task type.

Composed at runtime: `system = persona + "\n\n---\n\n" + task_prompt`.

### Alternatives considered

**Keep everything in one prompt file per node** — simpler file structure,
but the same persona content would need to be duplicated across every prompt
file for the same role, and any change to the persona requires updating
multiple files.

**Store personas in code as string constants** — loses the benefit of
plain-text editability by non-developers. A committee member who wants to
adjust how the chair's role is described should not need to edit a Python file.

### Consequences

- A single persona can be paired with multiple task prompts. The treasurer
  persona, for example, will eventually be combined with both a
  budget-drafting task and a financial-summary task.
- Non-developers can edit personas and task prompts independently without
  touching code.
- The `agent/personas/README.md` documents the convention and the code
  pattern for loading and composing the two layers. This is essential — the
  pattern is not self-evident from the file structure alone.
- Identity claims ("you are a...") must be removed from all task prompt files
  to avoid conflict with the persona layer. This is easy to forget when
  writing new task prompts.

## ADR-001-D: Asynchronous job pattern for the API

### Context

The full pipeline (fetch → infer → draft → review → possibly revise → save)
takes 60–120 seconds depending on the model and data volume. A synchronous
HTTP endpoint that held the connection open for this duration would time out
in most HTTP clients and proxies, and would provide no feedback to the caller
during processing.

### Decision

Use an asynchronous job pattern:
- `POST /agenda/generate` starts the pipeline in a background thread and
  returns a `job_id` immediately (under one second).
- `GET /agenda/status/{job_id}` allows the caller to poll for completion.

Job state is stored in an in-memory dictionary (`_jobs` in `main.py`).

### Alternatives considered

**Synchronous endpoint** — simpler to implement, but times out on slow
models and provides no progress visibility.

**WebSocket for real-time progress** — would allow the client to receive
node-by-node progress updates as the graph executes. More complex to
implement and consume. Deferred; the polling pattern is sufficient for
a monthly tool.

**Persistent job store (Redis, database)** — jobs would survive server
restarts. Unnecessary at current scale — if the server restarts during
a pipeline run, the job takes under two minutes to re-trigger. Add
persistent storage if this system runs at higher frequency or needs
audit trails.

### Consequences

- The n8n workflow implements the polling loop: trigger → wait 60s →
  poll → check completion → respond.
- The in-memory job store is lost on container restart. For a monthly
  workflow this is acceptable. Document this limitation clearly if the
  system is adopted for higher-frequency use.
- `job_id` is a UUID generated at request time. It provides no information
  about the job's content, which is intentional — job IDs should be opaque
  to callers.

## ADR-001-E: Structured outputs for LLM responses used in routing

### Context

Two nodes in the pipeline (`infer_tasks`, `review_draft`) produce outputs
that are consumed programmatically — as inputs to downstream nodes and as
the basis for routing decisions. If these outputs are free-form text, the
consuming code must parse natural language, which is brittle and
non-deterministic.

### Decision

Use Pydantic models (`TaskList`, `ReviewResult`) with LangChain's
`.with_structured_output()` for nodes whose output is consumed by code
rather than displayed to a user. The routing decision after `review_draft`
branches on `ReviewResult.passed`, which is a Python `bool`.

### Alternatives considered

**Parse free-form text** — asking the model to write "PASS" or "FAIL" and
matching with a string comparison. Fragile: models occasionally add
punctuation, whitespace, or extra words. The failure mode (a revision that
should have triggered doesn't) is silent and hard to debug.

**Structured output for all nodes** — applying `.with_structured_output()`
to the draft and revision nodes as well. Unnecessary — the output of those
nodes is text displayed to the user, not consumed by code. Structured output
adds overhead (an additional parsing step) without benefit for text-only outputs.

### Consequences

- Structured output relies on the model's function-calling capability.
  Most instruction-tuned models support this; very small models (under 3B
  parameters) may not reliably. If you switch to a smaller local model,
  validate that structured output still works.
- Pydantic validation errors from malformed model responses will surface
  as exceptions in the node. These should be caught and handled gracefully
  in a future iteration — currently they propagate to the job error field.
- The `TaskList` and `ReviewResult` schemas in `agent/state.py` are the
  contracts between the LLM and the rest of the pipeline. Changes to these
  schemas require corresponding changes to the prompts that instruct the
  model to populate them.

## ADR-001-F: Google Docs native tabs for document structure

### Context

Meeting notes and agendas are stored in Google Docs using the native tabs
feature: one top-level tab per year, nested sub-tabs per meeting
(e.g. "03/25/26"). This structure needs to be navigated programmatically
to fetch the correct meeting's content.

### Decision

Use the Google Docs API with `includeTabsContent=True` to fetch the full
tab tree, then recursively walk it to identify meeting tabs by parsing
dates from sub-tab titles. Meeting tabs are identified by the presence of
a parseable date in one of three formats: `MM/DD/YY`, `MM/DD/YYYY`,
`YYYY-MM-DD`.

### Alternatives considered

**Separate Google Doc per meeting** — would make fetching trivial (list
files in a folder, sort by date). Rejected because it would require
changing how the committee currently organizes its documents.

**Parse tab titles with a strict format requirement** — requiring all sub-tab
titles to follow a single date format. More robust but would require the
committee to rename existing tabs. The multi-format parser accepts the
formats that already exist in the documents.

**Heading-based structure in a single doc** — treating heading levels as the
structural delimiter rather than tabs. Fragile because heading usage is
inconsistent in practice and headings carry semantic meaning beyond structure.

### Consequences

- Sub-tab titles must contain a recognisable date for the fetcher to find
  them. Tabs named "General Notes" or "Miscellaneous" will be skipped.
  This is by design — only dated meeting tabs are relevant to agenda generation.
- The `_parse_tab_date` function is the single point of failure for document
  fetching. If it fails to parse a tab's date, that tab is silently skipped.
  Add logging here if meetings appear to be missing from the pipeline.
- The Google Docs tabs API (`includeTabsContent`) was introduced in 2024.
  If the API version changes, this is the first place to check.

## Decisions explicitly deferred

The following were considered and deliberately not implemented yet, following
the YAGNI principle:

| Decision | Reason deferred |
|---|---|
| Local database / caching | Fetch latency is seconds for monthly use; cache invalidation complexity not justified yet |
| Attachment processing | Upstream data quality issues take priority; attachments are a secondary signal |
| Parallel node execution | Sequential fetch latency is acceptable; add with LangGraph's Send API when it matters |
| Persistent job store | Monthly frequency doesn't justify the complexity |
| Full app verification with Google | Only needed if the app is distributed to users outside your Google account |
| Note-taking pipeline | Separate problem, separate sub-graph; modular design anticipates this extension |
